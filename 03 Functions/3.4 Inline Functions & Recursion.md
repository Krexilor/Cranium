## Overview
This file covers three function-related topics: **inline functions** (and what `inline` really means today), **compile-time functions and checks** (`constexpr`, `[[nodiscard]]`, `static_assert`, `assert`), and **recursion** (a function that calls itself to solve a problem through self-similar sub-steps).

## Inline Functions
Normally, calling a function involves overhead: jumping to a different memory location, pushing arguments onto the stack, and jumping back. For very small, frequently-called functions, this overhead can be larger than the function body itself.

The `inline` keyword **suggests** to the compiler that it should replace the function call with the function's actual code directly at the call site - eliminating call overhead entirely.

```cpp
inline int square(int n) {
    return n * n;
}

int main() {
    int result = square(5);
    // The compiler may replace this with: int result = 5 * 5;
    return 0;
}
```

> [!NOTE]
> As a speed hint, `inline` is largely historical. Modern compilers decide what to inline on their own, may ignore the keyword completely, and will inline many functions that do not have it.
>
> The keyword's real modern meaning is about **linking**: an `inline` function is allowed to be defined in several `.cpp` files, as long as every definition is identical. That is what makes it legal to put function definitions in header files (see 3.6).

### When Inlining Helps
* Very short functions (1 - 3 lines).
* Called extremely frequently (e.g., inside tight loops).
* Simple getters/setters in classes.

> [!WARNING]
> Overusing `inline` on large functions **increases binary size** (code duplication at every call site) and can actually hurt performance due to worse CPU instruction-cache behavior. Reserve it for genuinely small, hot-path functions.

## `constexpr` Functions (C++11)
A `constexpr` function **can** be evaluated at compile time when it is called with compile-time constants. When called with runtime values it works like an ordinary function.

```cpp
constexpr int square(int n) {
    return n * n;
}

constexpr int factorial(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) {     // loops and local variables are allowed since C++14
        result *= i;
    }
    return result;
}

constexpr int area = square(5);        // computed at compile time: 25
int table[square(3)] = {};             // array sizes must be constants: 9 elements

int n;
std::cin >> n;
std::cout << square(n) << "\n";             // still works (n = 7 prints 49)
```

> [!IMPORTANT]
> `constexpr` on a function means "*may* be evaluated at compile time", not "*will* be". It is guaranteed only in a context that **requires** a constant: a `constexpr` variable initializer, an array size, a `static_assert`, or a template argument. Elsewhere the compiler may still compute it at runtime. (C++20 adds `consteval`, which *forces* compile-time evaluation; it is covered in the Modern C++ topic.)

> [!NOTE]
> A `constexpr` function is implicitly `inline`, so it can be defined in a header. Its body must be simple enough to run at compile time: no input/output, for example.

## `[[nodiscard]]` (C++17)
`[[nodiscard]]` makes the compiler warn when a caller **ignores the return value**:

```cpp
[[nodiscard]] int divide(int a, int b) {
    return a / b;
}

divide(10, 2);  // warning: ignored nodiscard return value
int q = divide(10, 2);
```

Use it on functions whose result is the whole point (pure computations) or must be checked (error codes). It turns "forgot to use the result" bugs into compile-time warnings.

## Checking Assumptions: `static_assert` and `assert`

| Tool                        | Checked at   | On failure                                                          | Removed in release builds? |
| --------------------------- | ------------ | ------------------------------------------------------------------- | -------------------------- |
| `static_assert(cond, "msg")`| Compile time | Compile error showing your message                                  | Never                      |
| `assert(cond)` (`<cassert>`)| Runtime      | Prints the expression, file, function and line, then aborts         | Yes, when `NDEBUG` is defined |

```cpp
#include <cassert>

static_assert(factorial(5) == 120, "factorial(5) must be 120");    // condition must be a constant
static_assert(sizeof(int) >= 4, "this code assumes a 32-bit int");

int divide(int a, int b) {
    assert(b != 0 && "divisor must not be zero");                  // message shown when the assertion fails
    return a / b;
}

// divide(1, 0) at runtime prints something like:
// Assertion `b != 0 && "divisor must not be zero"' failed.   then the program aborts
```

> [!WARNING]
> `assert` catches **programmer errors** (a broken precondition), not bad user input or expected runtime failures; use input validation (2.3) or, later, exceptions for those. Because `assert` disappears when `NDEBUG` is defined (typical release builds, `-DNDEBUG`), the asserted expression must have **no side effects**: `assert(i++ < 10)` would stop incrementing `i` in release builds.

## Recursion
**Recursion** occurs when a function calls itself, breaking a problem down into smaller instances of the same problem until it reaches a **base case** that stops the recursion.

## Anatomy of a Recursive Function
Every correct recursive function needs:
1. A **base case** - the condition that stops further recursion.
2. A **recursive case** - where the function calls itself with a smaller/simpler input.

```cpp
int factorial(int n) {
    if (n <= 1) {                   // Base case
    return 1;
    }
    return n * factorial(n - 1);    // Recursive case
}

int main() {
    std::cout << factorial(5) << std::endl;   // Output: 120
    return 0;
}
```

### Tracing the Call Stack
```
factorial(5)
= 5 * factorial(4)
= 5 * (4 * factorial(3))
= 5 * (4 * (3 * factorial(2)))
= 5 * (4 * (3 * (2 * factorial(1))))
= 5 * (4 * (3 * (2 * 1)))
= 120
```

> [!IMPORTANT]
> Each recursive call adds a new **stack frame** to the call stack. Without a correct base case, this leads to infinite recursion and a **stack overflow** crash. Always verify the base case is reachable from every recursive path.

### Classic Example: Fibonacci Sequence
```cpp
int fibonacci(int n) {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}

int main() {
    for (int i = 0; i < 8; i++) {
    std::cout << fibonacci(i) << " ";
    }
    return 0;
}
```

> [!WARNING]
> Naive recursive Fibonacci is extremely inefficient - `O(2^n)` time complexity, because it recalculates the same values repeatedly. This is a common interview topic for introducing **memoization** and **dynamic programming** (covered later in Algorithms).

### Recursion vs Iteration
| Aspect               | Recursion                                     | Iteration (loops)                 |
| -------------------- | --------------------------------------------- | --------------------------------- |
| Readability counting | Often Cleaner for tree/graph-like problems    | Often cleaner for simple counting |
| Memory usage         | Higher - uses the call stack                  | Lower - constant stack space      |
| Performance          | Slightly slower (function call overhead)      | Generally faster                  |
| Best suited for      | Trees, graphs, divide & conquer, backtracking | Simple linear repetition          |

> [!TIP]
> A good rule of thumb: if a problem can be naturally expressed as "solve a smaller version of the same problem," recursion is likely the clearer choice. If it's simple repetition over a known range, prefer a loop for performance and stack safety.
