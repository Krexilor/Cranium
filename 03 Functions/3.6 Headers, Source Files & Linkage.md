## Overview
Every example so far fits in one `.cpp` file. Real programs are split across many files:
* **Header files** (`.h`) hold **declarations** - what exists.
* **Source files** (`.cpp`) hold **definitions** - how it works.

This keeps code organized, reusable, and faster to rebuild, because only the changed files are recompiled.

## A Three-File Program

```cpp
// mathutils.h
#ifndef MATHUTILS_H
#define MATHUTILS_H

int add(int a, int b);                 // declarations only
int square(int n);

#endif
```

```cpp
// mathutils.cpp
#include "mathutils.h"

int add(int a, int b) { return a + b; }        // definitions
int square(int n) { return n * n; }
```

```cpp
// main.cpp
#include <iostream>
#include "mathutils.h"

int main() {
    std::cout << add(3, 4) << " " << square(5) << "\n";     // 7 25
    return 0;
}
```

Build all `.cpp` files together:

```text
g++ -std=c++20 main.cpp mathutils.cpp -o app
```

* `#include <iostream>` - angle brackets: search the compiler's standard/system directories.
* `#include "mathutils.h"` - quotes: search the including file's folder first, then fall back to the system directories. Use quotes for your own headers.

> [!TIP]
> Keep a multi-file exercise in its own subfolder. If your build setup compiles only the active file (for example a VS Code task using `${file}`), multi-file programs need a command that compiles all the `.cpp` files, such as the one above. Build systems like CMake automate this (covered later).

## What the Build Really Does
Each `.cpp` file, together with everything it `#include`s, forms a **translation unit**. Every translation unit is compiled **independently** into an object file, and the **linker** then joins them (see 1.6 in your Introduction notes on the compilation stages):

```text
g++ -std=c++20 -c main.cpp         ->  main.o        (compile only)
g++ -std=c++20 -c mathutils.cpp    ->  mathutils.o
g++ main.o mathutils.o -o app                        (link)
```

If you edit only `mathutils.cpp`, only that file must be recompiled and relinked.

> [!NOTE]
> `#include` is a textual copy-paste performed by the preprocessor. A single `#include <iostream>` expands to roughly 43,000 lines with GCC 13 in C++20 mode. Headers should include only what they actually need.

## Compile Errors vs Linker Errors

| Stage    | Typical message (GCC)                                      | Usual cause                                                                   |
| -------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Compiler | `error: 'add' was not declared in this scope`              | Used a function with no declaration in this file (missing `#include`)         |
| Linker   | ``undefined reference to `add(int, int)' ``                | Declared but never defined, or the `.cpp` was not compiled/linked, or the signature differs between declaration and definition |
| Linker   | ``multiple definition of `twice(int)' ``                   | Defined in more than one translation unit                                     |

For example, `g++ main.cpp -o app` (forgetting `mathutils.cpp`) compiles `main.cpp` fine but fails at link time with `undefined reference to 'add(int, int)'` and `undefined reference to 'square(int)'`.

## Header Guards
A header can easily be included **twice** in one translation unit through different paths:

```cpp
// config.h
constexpr int MAX_USERS = 100;
```
```cpp
// a.h
#include "config.h"
int fromA();
```
```cpp
// b.h
#include "config.h"
int fromB();
```
```cpp
// main.cpp
#include "a.h"
#include "b.h"                         // config.h now arrives a second time
```

```text
config.h:1:15: error: redefinition of 'constexpr const int MAX_USERS'
```

The fix is a **header guard** at the top of every header:

```cpp
// Option 1: classic include guard (standard C++)
#ifndef CONFIG_H
#define CONFIG_H

constexpr int MAX_USERS = 100;

#endif

// Option 2: #pragma once
#pragma once

constexpr int MAX_USERS = 100;
```

* With an include guard, the second inclusion is skipped because the macro is already defined. The macro name must be **unique** across the project (`FILENAME_H` or `PROJECT_FILENAME_H`).
* `#pragma once` is not part of the C++ standard, but GCC, Clang, and MSVC all support it. It is shorter and cannot suffer from name clashes, so it is a common choice. Pick one style and use it in **every** header.

## What Goes Where

| In the header (`.h`)                               | In the source file (`.cpp`)                          |
| -------------------------------------------------- | ---------------------------------------------------- |
| Function **declarations**                          | Function **definitions**                             |
| `const` / `constexpr` constants                    | Definitions of non-constant global variables         |
| `inline` and `constexpr` function definitions      | Helper functions private to the file                 |
| `extern` variable declarations                     | The single definition of each `extern` variable      |
| Class definitions and templates (later topics)     | Member function definitions (later topic)            |
| `#include`s the header itself needs                | `#include`s only the `.cpp` needs                    |

> [!WARNING]
> Defining an ordinary function **in a header** breaks the build as soon as two `.cpp` files include it:
> ```cpp
> // bad.h
> #pragma once
> int twice(int x) { return x * 2; }     // a definition, not just a declaration
> ```
> ```text
> multiple definition of `twice(int)'; g1.cpp first defined here
> ```
> Header guards do **not** prevent this, because they only stop double inclusion *within one* translation unit. Fix it by marking the function `inline` (an `inline` definition may appear in every file, see 3.4) or by moving the definition into a `.cpp` file.

## The One Definition Rule (ODR)
* Every non-`inline` function and every variable used by the program must be defined **exactly once** in the whole program.
* Types, `inline` functions, `inline` variables, and templates may be defined in many translation units, but the definitions must be **identical**.

Violating the ODR gives linker errors in the good case, and silently inconsistent behavior in the bad case (the compiler is not required to diagnose it).

## Linkage
**Linkage** decides whether a name in one translation unit refers to the same entity in another.

| Linkage      | Meaning                                    | Applies to                                                                                      |
| ------------ | ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| **External** | Visible to all translation units           | Functions and non-`const` globals (the default)                                                |
| **Internal** | Visible only inside its own file           | `static` functions/variables at namespace scope, anonymous namespaces (3.5), `const`/`constexpr` globals |
| **None**     | Not shared                                 | Local variables                                                                                 |

Two files can each have their own private function with the same name:

```cpp
// j1.cpp
static int helper() { return 1; }
int one() { return helper(); }

// j2.cpp
static int helper() { return 2; }     // a different, separate helper
int two() { return helper(); }

// main prints "12" - no clash, because both helpers have internal linkage
```

### Sharing a Global Variable
When a global genuinely must be shared, **declare** it with `extern` in the header and **define** it once in a source file:

```cpp
// globals.h
#pragma once
extern int counter;                    // declaration: "defined in some .cpp"
inline int hits = 0;                   // C++17 inline variable: a definition in a header is allowed
constexpr int LIMIT = 10;              // internal linkage: each .cpp gets its own copy
```

```cpp
// globals.cpp
#include "globals.h"

int counter = 0;                       // the single definition of counter

void bump() {
    counter++;
    hits++;
}
```

```cpp
// main.cpp
#include <iostream>
#include "globals.h"

void bump();

int main() {
    bump();
    bump();
    std::cout << counter << " " << hits << " " << LIMIT << "\n";     // 2 2 10
}
```

> [!WARNING]
> Writing `int total = 0;` in a header (no `extern`, no `inline`) defines `total` in every file that includes it, giving ``multiple definition of `total' `` at link time.

> [!NOTE]
> For a constant that must be a **single shared object** across all files (so its address is the same everywhere), use `inline constexpr int LIMIT = 10;` (C++17). Shared mutable globals still carry every downside listed in 3.5, so prefer parameters.

## Header Hygiene Checklist
* Guard **every** header with `#pragma once` or an include guard.
* A header includes only what its own declarations need; a `.cpp` includes the rest.
* In a `.cpp`, include its **own header first**. This exposes a header that forgot one of its own `#include`s.
* Never `#include` a `.cpp` file.
* Never put `using namespace ...;` in a header (3.5).
* A function's declaration and definition must match **exactly**; a different parameter list defines a *different* overload and shows up as a linker error.
* Write **default arguments** (3.3) only in the declaration (the header), not again in the definition.
