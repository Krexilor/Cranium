## Overview
Two different questions are easy to confuse:
* **Scope** - *where* in the source code a name can be used (a compile-time property).
* **Lifetime** - *how long* the object actually exists in memory (a runtime property).

A variable can be out of scope but still alive (a `static` local), or in scope but already dead (a dangling pointer from Topic 5). This file covers both, then namespaces.

## Block Scope
A name declared inside `{ }` is visible from its declaration to the closing brace.

```cpp
int main() {
    int a = 1;                         // visible until the end of main
    {
        int b = 2;                     // visible only inside this inner block
        std::cout << a << b << "\n";        // both visible
    }
    // cout << b;                      // ERROR: 'b' was not declared in this scope
    return 0;
}
```

Function parameters are scoped to the function body, and a variable declared in a `for` header is scoped to the loop:

```cpp
for (int i = 0; i < 3; i++) { }
// cout << i;                          // ERROR: 'i' was not declared in this scope
```

## Shadowing
An inner declaration with the same name **hides** the outer one:

```cpp
int counter = 100;                     // global

int main() {
    int counter = 1;                   // shadows the global counter
    {
        int counter = 2;               // shadows the local counter above
        std::cout << counter << "\n";       // 2
    }
    std::cout << counter << "\n";           // 1
    std::cout << ::counter << "\n";         // 100 (:: reaches the global scope)
    return 0;
}
```

> [!WARNING]
> Shadowing is legal, but it makes it easy to modify the wrong variable. Avoid reusing names across nested scopes. GCC and Clang can warn about it with `-Wshadow`.

## Global Variables
A variable declared outside every function has **global (namespace) scope**: it is visible from its declaration to the end of the file.

```cpp
int totalScore = 0;                    // global

void addPoints(int p) {
    totalScore += p;                   // any function can read and change it
}
```

* Globals are **zero-initialized** by default, unlike locals, which hold garbage unless you initialize them.
* They exist for the **entire program run**.

> [!WARNING]
> Mutable globals create hidden dependencies: any function can change them, so bugs are hard to trace, code is hard to test, and names collide easily. Prefer passing values through parameters and return values. Global **constants** (`const` / `constexpr`) are fine.

> [!NOTE]
> The initialization order of global variables defined in *different* `.cpp` files is unspecified. Never let one global's initial value depend on a global from another file.

## Storage Duration
**Storage duration** is the rule that decides an object's lifetime:

| Duration      | Applies to                                         | Lives from → until                         | Typical location (see 5.5) | Default value         |
| ------------- | -------------------------------------------------- | ------------------------------------------ | -------------------------- | --------------------- |
| **Automatic** | Local variables, parameters                        | Declaration → end of its block             | Stack                      | Garbage (uninitialized) |
| **Static**    | Globals, `static` locals, namespace-scope variables | Program start → program end                | Data segment               | Zero                  |
| **Dynamic**   | Objects created with `new`                         | `new` → `delete`                           | Heap                       | Garbage (uninitialized) |
| **Thread**    | `thread_local` variables                           | Thread start → thread end                  | Per-thread storage         | Zero                  |

> [!NOTE]
> This is why a leaked heap object (5.4) outlives the pointer that held it: the pointer has automatic duration and vanishes at the end of its block, while the object has dynamic duration and stays until `delete`.

## `static` Local Variables
A `static` local is initialized **once**, the first time execution reaches it, and then keeps its value between calls. Its **scope** is still local, but its **lifetime** is the whole program.

```cpp
int callCount() {
    static int calls = 0;              // initialized ONCE
    calls++;
    return calls;
}

int plain() {
    int calls = 0;                     // re-created on every call
    calls++;
    return calls;
}

callCount();
callCount();
std::cout << callCount() << "\n";           // 3
std::cout << plain() << plain() << "\n";    // 11
```

Typical uses are counters, ID generators, and one-time initialization or caches.

> [!WARNING]
> A `static` local is hidden state: the function no longer depends only on its arguments, which makes it harder to test and reason about, and it is not safe to modify from several threads without protection.

> [!NOTE]
> The keyword `static` means different things in different places: a `static` **local** (this section) controls lifetime, a `static` at **namespace scope** controls linking (3.6), and `static` **class members** are covered in the OOP topic.

## Scope vs Lifetime Summary

| Variable                     | Scope (where visible)                  | Lifetime (how long it exists)          |
| ---------------------------- | -------------------------------------- | -------------------------------------- |
| Local variable               | Its block                              | Until the block ends                   |
| `static` local variable      | Its block                              | Whole program                          |
| Global variable              | Declaration to end of file             | Whole program                          |
| Object created with `new`    | Wherever a pointer/reference is visible | Until `delete`                         |

## Namespaces
A **namespace** groups names under a label, so identical names in different libraries do not collide.

```cpp
namespace audio {
    void play() { std::cout << "audio::play\n"; }
    int volume = 7;
}

namespace video {
    void play() { std::cout << "video::play\n"; }

    namespace codec {                  // namespaces can be nested
        int id = 42;
    }
}

audio::play();                         // audio::play
video::play();                         // video::play
std::cout << video::codec::id << "\n";      // 42
```

Since C++17, nested namespaces can be written in one line: `namespace video::codec { ... }`.

### Three Ways to Use Names from a Namespace

| Style                  | Example                  | Effect                                              |
| ---------------------- | ------------------------ | --------------------------------------------------- |
| Qualified name         | `std::cout`              | Always unambiguous                                  |
| `using` declaration    | `using std::cout;`       | Brings in **one** name                              |
| `using` directive      | `using namespace std;`   | Brings in **every** name; risks collisions          |

```cpp
using audio::volume;                   // using declaration: only this one name
std::cout << volume << "\n";                // 7
```

### Namespace Aliases

```cpp
namespace vc = video::codec;
std::cout << vc::id << "\n";                // 42
```

### Anonymous Namespaces
Names in a namespace without a label are visible **only inside the current file**:

```cpp
namespace {
    int hidden = 5;                    // not accessible from other .cpp files
    void helper() { }
}
```

This is the modern replacement for file-level `static` (see "Linkage" in 3.6).

> [!WARNING]
> `using namespace std;` is acceptable in small single-file programs like the ones in these notes. In real projects, and **never in a header file**, prefer `std::` prefixes or targeted `using` declarations, because a `using namespace` in a header forces its effect on every file that includes it.

> [!NOTE]
> `std` is the namespace of the whole standard library (`std::cout`, `std::string`, `std::vector`, ...). Never add your own names to it.
