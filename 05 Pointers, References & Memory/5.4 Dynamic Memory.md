## Overview
All variables declared normally (e.g., `int x = 5;`) live on the **stack** - their lifetime is tied to the scope they're declared in and they're automatically destroyed when that scope ends. **Dynamic memory** lets you allocate memory on the **heap** at runtime, giving you full control over when that memory is created and when it is released - independent of any scope.

## Why Dynamic Memory?
Stack memory has two key limitations:
1. **Fixed size** - must be known at compile time (you can't declare `int arr[n]` where `n` comes from user input in standard C++).
2. **Tied to scope** - destroyed automatically when the block ends, whether you want it to or not.

Heap memory solves both: you can allocate any size at runtime, and it persists until you explicitly free it.

## `new` - Allocating on the Heap
The `new` operator allocates memory on the heap and returns a **pointer** to it.

```cpp
// Allocate a single int on the heap
int* a = new int;          // memory allocated, value uninitialized (garbage)
int* b = new int(42);      // allocated and initialized to 42
int* c = new int{};        // allocated and zero-initialized

std::cout << *b << std::endl;        // 42
```

```cpp
// Allocate a single double
double* dptr = new double(3.14);
std::cout << *dptr << std::endl;     // 3.14
```

> [!NOTE]
> Heap memory is **not automatically initialized** unless you ask for it. The initializer you write decides what you get:
>
> | Expression               | Result                          |
> | ------------------------ | ------------------------------- |
> | `new int`                | One uninitialized (garbage) int |
> | `new int()` / `new int{}`| One int, set to `0`             |
> | `new int(42)`            | One int, set to `42`            |
> | `new int[4]`             | 4 uninitialized ints            |
> | `new int[4]()` / `new int[4]{}` | 4 ints, all `0`          |
> | `new int[3]{1, 2, 3}`    | 3 ints holding `1, 2, 3`        |

## `delete` - Releasing Heap Memory
When you're done with heap memory, you **must** release it using `delete`. Failing to do so causes a **memory leak** - the memory stays allocated for the entire program lifetime even though nothing uses it.

```cpp
int* ptr = new int(42);
std::cout << *ptr << std::endl;       // 42

delete ptr;       // release the heap memory
ptr = nullptr;    // immediately null the pointer (safe practice)
```

> [!WARNING]
> Forgetting to call `delete` is a **memory leak**. In long-running applications (servers, games, OS services), leaks accumulate over time until the process runs out of memory and crashes. This is one of the most common and hardest-to-debug issues in C++ programs.

## Dynamic Arrays with `new[]` and `delete`
To dynamically allocate an array whose size is determined at runtime, use `new[]`.

```cpp
int n;
std::cout << "Enter array size: ";
std::cin >> n;

int* arr = new int[n];   // allocates n ints on the heap at runtime

for (int i = 0; i < n; i++) {
    arr[i] = i * 10;
}

for (int i = 0; i < n; i++) {
    std::cout << arr[i] << " ";
}

delete[] arr;      // MUST use delete[] for arrays, not plain delete
arr = nullptr;
```

> [!WARNING]
> **Always match** `new[]` **with** `delete[]` - never with plain `delete`. Using `delete` on a `new[]`-allocated array is undefined behavior. It may only destroy the first element and corrupt the heap. Similarly, use plain `delete` only for single objects allocated with plain `new`.

| Allocation | Deallocation   |
| ---------- | -------------- |
| `new T`    | `delete ptr`   |
| `new T[n]` | `delete[] ptr` |

## Allocating Objects on the Heap
`new` works with any type, including classes and structs.

```cpp
struct Point {
    int x, y;
};

Point* p = new Point{3, 7};
std::cout << p->x << ", " << p->y << std::endl;    // 3, 7

delete p;
p = nullptr;
```

> [!NOTE]
> The `->` operator is shorthand for dereferencing a pointer and then accessing a member: `p->x` is equivalent to `(*p).x`. It's used whenever you access members through a pointer.

## When `new` Fails
Heap memory is finite. By default, `new` **never returns `nullptr`**: when it cannot provide the memory it throws a `std::bad_alloc` exception.

```cpp
#include <new>

std::size_t huge = static_cast<std::size_t>(1) << 45;        // 2^45 ints (about 128 TB)

try {
    int* big = new int[huge];
    delete[] big;
}
catch (const bad_alloc& e) {
    std::cout << "caught: " << e.what() << "\n";        // caught: std::bad_alloc
}
```

`try` / `catch` is covered in Topic 8. Until then, remember that an uncaught `bad_alloc` terminates the program, and that checking `if (ptr == nullptr)` after a plain `new` is pointless.

The `nothrow` form returns `nullptr` instead of throwing:

```cpp
int* big = new(nothrow) int[huge];
if (big == nullptr) {
    std::cout << "allocation failed\n";
}
```

> [!NOTE]
> Even the `nothrow` form still throws `std::bad_array_new_length` if the requested array length is itself invalid (for example, a size so large that `length * sizeof(int)` overflows). On some operating systems with memory overcommit, a very large allocation can also appear to succeed and only fail later, when the memory is first used.

## `new` / `delete` vs `malloc` / `free`
C provides its own heap functions in `<cstdlib>`, and you will see them in C libraries and older code:

```cpp
#include <cstdlib>

int* m = static_cast<int*>(malloc(sizeof(int) * 3));    // 3 ints: size in BYTES, returns void*
m[0] = 7;
free(m);
```

| Aspect                         | `new` / `delete`                     | `malloc` / `free`                      |
| ------------------------------ | ------------------------------------ | -------------------------------------- |
| Origin                         | C++                                  | C                                      |
| Return type                    | Typed pointer (`int*`)               | `void*` (needs a cast in C++)          |
| Size argument                  | Element count: `new int[3]`          | Bytes: `3 * sizeof(int)`               |
| Constructors / destructors     | **Runs them** (Topic 6)              | Never runs them                        |
| On failure                     | Throws `std::bad_alloc`              | Returns `nullptr`                      |
| Release with                   | `delete` / `delete[]`                | `free`                                 |

> [!WARNING]
> Never mix the two families. Calling `delete` on memory from `malloc`, or `free` on memory from `new`, is undefined behavior. In C++ code, prefer containers and smart pointers, then `new` / `delete`; use `malloc` only when a C API requires it.

## Stack vs Heap - Side by Side

```cpp
// Stack allocation
void stackExample() {
    int x = 42;      // on the stack
    // x is destroyed automatically when this function returns
}

// Heap allocation
void heapExample() {
    int* ptr = new int(42);   // on the heap
    // The local pointer is destroyed when the function returns.
    // The heap-allocated int survives and must be deleted explicitly.
    delete ptr;
}
```

| Aspect            | Stack                                | Heap                                 |
| ----------------- | ------------------------------------ | ------------------------------------ |
| Speed             | Very fast (just moves stack pointer) | Slower (general allocator overhead)  |
| Size limit        | Small (typically 1-8 MB)             | Large (limited by system RAM)        |
| Lifetime          | Tied to the enclosing scope          | Manual - you control when it's freed |
| Allocation syntax | `int x = 5;`                         | `int* ptr = new int(5)`              |
| Deallocation      | Automatic                            | Manual - `delete ptr;`               |
| Risk              | Stack overflow (too much nesting)    | Memory leaks, dangling pointers      |

## Memory Leaks in Practice

```cpp
void leakyFunction() {
    int* ptr = new int(42);
    // forgot to delete - this allocation leaks every time the function is called
}

int main() {
    for (int i = 0; i < 1000000; i++) {
        leakyFunction();    // 1,000,000 allocations leaked by the end of this loop
    }
    return 0;
}
```

> [!NOTE]
> Each `new int` asks for 4 bytes, but the allocator rounds the request up and adds bookkeeping, so the real cost is much larger. On GCC 13 / Linux, this loop grew the process by about 30 MB (roughly 32 bytes per leaked `int`).

## Ownership and a Preview of RAII
A pointer returned by `new` carries an **obligation**: exactly one part of the program must eventually `delete` it. That part is the object's **owner**. A raw pointer that merely *looks at* an object, without deleting it, is a **non-owning** pointer.

Leaks usually come from paths where the owner never reaches its `delete`:

```cpp
void process(bool failEarly) {
    int* data = new int[100];
    if (failEarly) {
        return;                        // LEAK: this path skips the delete[]
    }
    delete[] data;
}
```

AddressSanitizer's leak checker reports this as `Direct leak of 400 byte(s) in 1 object(s)`.

The C++ answer is **RAII** (Resource Acquisition Is Initialization): tie the resource to an **object**. The object acquires the resource in its constructor and releases it in its destructor, and the destructor runs automatically at the end of the scope, on **every** path out. You have already been using this: `std::string` (4.5) and `std::vector` (4.6) own heap memory and free it themselves.

Smart pointers apply the same idea to a single heap object (a preview; they are covered in Topic 9):

```cpp
#include <memory>

void process(bool failEarly) {
    auto data = std::make_unique<int[]>(100);    // owns the 100 ints
    if (failEarly) {
        return;                             // fine: data's destructor frees the memory
    }
    data[0] = 1;
}                                           // no delete anywhere, and no leak on any path
```

Constructors and destructors themselves come in Topic 6.

| Situation                                   | Prefer                                              |
| ------------------------------------------- | --------------------------------------------------- |
| A single value or object with a known scope | An ordinary stack variable                          |
| A sequence of items, size known at runtime  | `std::vector`                                       |
| Text                                        | `std::string`                                       |
| A single object that must live on the heap  | `std::unique_ptr` (Topic 9)                         |
| Low-level code, or learning how it works    | Raw `new` / `delete`, with a clear owner            |

> [!TIP]
> Tools such as **Valgrind** (Linux/macOS) and **AddressSanitizer** (`-fsanitize=address` in GCC and Clang; MSVC has a similar option) detect memory leaks and invalid memory access at runtime. They are covered in the debugging and tooling material later in this roadmap. In day-to-day modern C++, containers and smart pointers make most manual `new` / `delete` unnecessary.
