## Overview
This file covers two connected ideas. First, how `const` combines with pointers, which is easy to get wrong. Second, the two remaining C++ casts that operate on pointers: `const_cast` and `reinterpret_cast`. (`static_cast` is in 2.7, and `dynamic_cast` arrives with inheritance in Topic 7.)

## `const` and Pointers
A pointer involves **two** things that can each be `const`: the **data** it points to, and the **pointer** itself.

| Declaration            | Read as                         | Change `*p`? | Re-point `p`? |
| ---------------------- | ------------------------------- | :----------: | :-----------: |
| `int* p`               | pointer to int                  | Yes          | Yes           |
| `const int* p`         | pointer to **const** int        | **No**       | Yes           |
| `int* const p`         | **const** pointer to int        | Yes          | **No**        |
| `const int* const p`   | const pointer to const int      | **No**       | **No**        |

`int const* p` is just another spelling of `const int* p`. A reliable way to read these is **right to left**: in `int* const p`, `p` is a `const` pointer to `int`. In `const int* p`, `p` is a pointer to an `int` that is `const`.

```cpp
int x = 10, y = 20;

const int* pc = &x;                    // pointer to const int
pc = &y;                               // OK: the pointer may be re-pointed
// *pc = 5;                            // ERROR: assignment of read-only location '*pc'

int* const cp = &x;                    // const pointer to int
*cp = 11;                              // OK: the data may be changed
// cp = &y;                            // ERROR: assignment of read-only variable 'cp'

const int* const cpc = &x;             // neither can change
```

### Conversions
You may add `const`, but you may not silently remove it:

```cpp
int a = 1;
const int* ro = &a;                    // OK: a read-only view of a non-const object

const int k = 5;
// int* bad = &k;                      // ERROR: invalid conversion from 'const int*' to 'int*'

const char* s = "text";
// char* t = s;                        // ERROR: invalid conversion from 'const char*' to 'char*'
```

> [!NOTE]
> A `const int*` promises only that **this pointer** will not be used to modify the value. The object itself may still change through another name (such as `a` above). It is a read-only view, not a guarantee that the data never changes.

### Why It Matters: Const Correctness
Declare everything `const` that does not need to change. It documents intent, lets the compiler catch accidental writes, and lets functions accept both const and non-const arguments:

```cpp
void printAll(const int* arr, int size) {      // promises not to modify the array
    for (int i = 0; i < size; i++) {
        std::cout << arr[i] << " ";
    }
}

int buffer[3] = {1, 2, 3};
printAll(buffer, 3);                           // a mutable array converts to const int*
```

`const int*` is also the pointer counterpart of the `const T&` parameter from 5.2. References cannot be re-seated at all, so there is no "const reference" in the `int* const` sense.

## `const_cast`
`const_cast<T>` is the only cast that can **add or remove** `const` (or `volatile`). It changes nothing else.

```cpp
const int k = 5;
// int* p = static_cast<int*>(&k);     // ERROR: static_cast cannot remove const
int* p = const_cast<int*>(&k);         // compiles; whether USING p is legal is a separate question
```

### The One Legitimate Use
Calling an old API that is *declared* with a non-const pointer but never modifies the data:

```cpp
void legacyPrint(char* text) {                 // old C-style API: forgot to say const
    std::cout << text << "\n";
}

char text[] = "legacy";
const char* view = text;
legacyPrint(const_cast<char*>(view));          // legacy
```

### The Undefined-Behavior Trap
Removing `const` is safe only if the object **was not originally const** and nothing writes through the pointer unless it should. **Modifying an object that was defined `const` is undefined behavior:**

```cpp
const int fixed = 10;
int* sneaky = const_cast<int*>(&fixed);
*sneaky = 20;                                  // UNDEFINED BEHAVIOR
std::cout << fixed << " " << *sneaky << "\n";       // GCC 13 printed: 10 20
```

The two lines printing different values for what looks like one memory location is a typical result: the compiler is allowed to replace reads of a `const` object with its initial value.

> [!WARNING]
> Needing `const_cast` almost always signals a design problem. Fix the declaration (add the missing `const` to the API) instead, and reserve the cast for code you cannot change.

## `reinterpret_cast`
`reinterpret_cast<T>` tells the compiler to **treat a bit pattern as a different type**. It performs no conversion, no checking, and no adjustment. It is the most dangerous cast, and the compiler accepts nearly anything:

```cpp
int a = 1;
// long* l = static_cast<long*>(&a);          // ERROR: static_cast cannot change pointer type
float* f = reinterpret_cast<float*>(&a);      // compiles with no warning at all
```

### Legitimate Uses
**1. Inspecting the raw bytes of an object** through `unsigned char*`:

```cpp
int value = 0x01020304;
unsigned char* bytes = reinterpret_cast<unsigned char*>(&value);

for (std::size_t i = 0; i < sizeof(value); i++) {
    std::cout << static_cast<int>(bytes[i]) << " ";     // 4 3 2 1
}
```

The lowest byte comes first: this machine is **little-endian** (true of x86-64 and most ARM systems).

**2. Converting a pointer to an integer and back** (`<cstdint>`):

```cpp
std::uintptr_t address = reinterpret_cast<std::uintptr_t>(&value);
int* back = reinterpret_cast<int*>(address);
std::cout << (back == &value) << "\n";                  // 1
```

**3.** Low-level code: hardware registers at fixed addresses, binary protocols, and C APIs.

### The Strict-Aliasing Trap
Reading or writing an object through a pointer of an **unrelated type** is undefined behavior (the *strict aliasing* rule):

```cpp
int a = 1;
float* f = reinterpret_cast<float*>(&a);
*f = 1.0f;                             // UNDEFINED BEHAVIOR, and the compiler did not warn
```

The only exception is looking at an object's bytes through `char`, `unsigned char`, or `std::byte` pointers, as in the previous example.

### The Safe Alternatives for Type Punning
To reinterpret the bits of one value as another type, copy them:

```cpp
#include <bit>
#include <cstring>

float f = 1.0f;

uint32_t bits = bit_cast<uint32_t>(f);         // C++20: type-safe, checked at compile time
uint32_t bits2;
memcpy(&bits2, &f, sizeof(f));                 // works in every C++ version

std::cout << hex << bits << " " << bits2 << dec << "\n";    // 3f800000 3f800000
```

`bit_cast` requires both types to have the same size and to be trivially copyable.

## All the Casts Together

| Cast               | What it does                         | Checked        | Typical use                                      | Main danger                                     |
| ------------------ | ------------------------------------ | -------------- | ------------------------------------------------ | ----------------------------------------------- |
| `static_cast`      | Conversions between related types    | Compile time   | Numeric conversions, `void*` to `T*`             | Low                                             |
| `const_cast`       | Adds or removes `const`              | Compile time   | Legacy APIs                                      | Modifying a truly const object is UB            |
| `reinterpret_cast` | Reinterprets bits / addresses        | **Not at all** | Byte inspection, pointer-integer conversion      | Strict-aliasing UB, non-portable results        |
| `dynamic_cast`     | Safe downcast in class hierarchies   | Runtime        | Inheritance (Topic 7)                            | Needs `virtual` functions                       |
| `(T)x` C-style     | Whichever of the first three works   | Varies         | **Avoid**                                        | Hides which dangerous cast just happened        |

> [!IMPORTANT]
> Choose the **weakest** cast that does the job: `static_cast` first, and the others only with a clear reason. Every cast is a statement that you know better than the type system, so a short comment explaining *why* it is safe is good practice.
