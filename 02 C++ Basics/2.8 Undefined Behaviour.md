## Overview
Not every mistake in C++ is something the compiler rejects. Code can compile cleanly, run, and even print the "right" answer while being **wrong**. The C++ standard sorts program behavior into four categories, and knowing which one you are in is essential.

| Category                   | What the standard says                                                  | Example                                                                 |
| -------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Well-defined**           | The result is fully specified                                           | `5 / 2` is `2`; `unsigned` overflow wraps around                        |
| **Implementation-defined** | The result varies by compiler/platform, and the compiler must document it | `sizeof(int)`, `sizeof(long)` (4 on 64-bit Windows, 8 on 64-bit Linux), whether plain `char` is signed |
| **Unspecified**            | Several valid results are allowed; the compiler need not document or be consistent | The order in which function arguments are evaluated                 |
| **Undefined (UB)**         | The standard places **no requirements at all**                          | Out-of-bounds array access, dereferencing `nullptr`, signed overflow    |

## Unspecified Behavior

```cpp
int a() { std::cout << "a "; return 1; }
int b() { std::cout << "b "; return 2; }
int add(int x, int y) { return x + y; }

int main() {
    int r = add(a(), b());      // which is called first, a() or b()?
    std::cout << "\nresult = " << r << "\n";
    return 0;
}

// GCC 13 printed:  b a
// Another compiler (or another version) may print:  a b
```

The result `3` is always the same, but the *order of side effects* is not guaranteed. Code must never depend on it.

## What Undefined Behavior Means
When a program triggers UB, the C++ standard no longer says anything about what the program does. Anything can happen:

* it crashes (the *lucky* outcome),
* it produces a wrong result,
* it appears to work perfectly,
* it behaves differently on another machine, another compiler, or only in release builds,
* it breaks only after an unrelated change elsewhere.

> [!IMPORTANT]
> "It ran fine when I tested it" proves nothing about code that contains UB. A program that appears to work is one of the valid outcomes.

### Why Does UB Exist?
C++ does not insert runtime checks for array bounds, null pointers, overflow, and so on, because checks cost speed. In exchange, the compiler is allowed to **assume your program never triggers UB**, and it optimizes based on that assumption:

```cpp
bool willOverflow(int x) {
    return x + 1 < x;           // intended: detect overflow
}
```

Signed overflow is UB, so the compiler may reason that `x + 1` can never be smaller than `x` and compile this function to simply `return false;`. GCC 13 at `-O2` does exactly that. The check meant to catch the bug is deleted *because* of the bug.

```cpp
// Correct: check BEFORE the operation, without overflowing
#include <limits>
bool willOverflow(int x) {
    return x == std::numeric_limits<int>::max();
}
```

> [!NOTE]
> The same check on an `unsigned` value is *not* removed, because unsigned overflow is well-defined (it wraps).

## Catalog of Undefined Behavior

| Undefined behavior                                        | Covered in            | How to avoid it                                       |
| --------------------------------------------------------- | --------------------- | ----------------------------------------------------- |
| Reading an uninitialized variable                         | 2.2                   | Initialize every variable at declaration              |
| Signed integer overflow                                   | 2.2                   | Use a wider type, or check before the operation       |
| Integer division or modulo by zero                        | This section          | Check the divisor first                               |
| Shifting by a negative amount or by >= the bit width      | 2.4                   | Validate the shift count; use unsigned types          |
| Floating-point value out of range converted to an integer | 2.7                   | Range-check before converting                         |
| Out-of-bounds array access                                | 4.1, 4.2              | Validate indices; track array sizes                   |
| Reaching the end of a non-`void` function without `return`| This section          | Return a value on every path                          |
| Dereferencing `nullptr`                                   | 5.3                   | Check pointers before use                             |
| Using a dangling pointer or reference                     | 5.3                   | Never return the address of a local; null after `delete` |
| Deleting the same pointer twice                           | 5.3                   | Set to `nullptr` after `delete`                       |
| Mismatching `new[]` with `delete` (or `new` with `delete[]`) | 5.4                | Always pair `new` / `delete` and `new[]` / `delete[]` |
| Pointer arithmetic outside the array (past one-past-the-end) | 5.1                | Stay within the array bounds                          |
| Modifying an object that was declared `const`             | Later (`const_cast`)  | Never write through a cast-away `const` on a true constant |

### Missing `return` Example
```cpp
int sign(int x) {
    if (x > 0) return 1;
    if (x < 0) return -1;
    // x == 0: control reaches the end with no return -> UNDEFINED BEHAVIOR
}
```

Only `main` is exempt: reaching its end implicitly returns `0`.

## Habits That Keep You Out of UB
* Initialize every variable and every pointer (`nullptr` if nothing else).
* Check indices, divisors, and pointers *before* using them.
* Avoid casts and keep signed and unsigned values separate (2.7).
* Do not write code that depends on evaluation order, such as modifying a variable twice in one expression (`i = i++ + ++i`). The rules for this have changed between standards, and it is never worth relying on.
* Compile with warnings enabled (`-Wall -Wextra`) and treat them as bugs.

> [!TIP]
> Tools can detect many kinds of UB at runtime. GCC and Clang provide **UndefinedBehaviorSanitizer** and **AddressSanitizer** (`-fsanitize=undefined,address`), which catch signed overflow, bad shifts, out-of-bounds access, and use-after-free while the program runs. They are covered later in the debugging material.
